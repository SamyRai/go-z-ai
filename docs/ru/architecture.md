## Структура пакетов

```text
main.go               Entrypoint: sets build info, then internal/cli.Execute()
internal/cli/         Cobra commands (package cli), one file per command group:
                      chat.go, models.go, usage.go, validate.go, accounts_cli.go,
                      coding_cli.go, coding_mcp_cli.go, ...; common.go holds the
                      shared plumbing, root.go the global flags
pkg/client/           The Go library — no CLI/TUI dependency, stdlib-only
                      (no third-party imports); layout below
pkg/observe/          OpenTelemetry Hook implementation (otel.go; depends on
                      go.opentelemetry.io/otel); separate package so pkg/client
                      stays stdlib-only
internal/accounts/    Multi-account credential store (~/.config/zai-client/accounts.json —
                      dir kept as zai-client for upgrade compat)
internal/atomicfile/  Atomic temp-file-then-rename writes (Write, WriteWithBackup)
                      used by every credential store and tool-config writer
internal/coding/      GLM Coding Plan credential store, the tool registry (one
                      tool_*.go file per tool), and Z.AI's MCP servers
internal/fileinput/   FileOrURL: a URL passes through, a local path is base64-encoded —
                      shared by `ocr parse`, `chat create --image/--video/--file`,
                      and the TUI media tab
internal/modelview/   Presentation helpers for model metadata (token counts, prices,
                      capability names) — shared by the CLI and the TUI
internal/usageview/   Presentation helpers for quota and usage (time windows, heat maps,
                      quota summaries, peak-hours logic) — shared by the CLI and the
                      TUI so their output can never drift
internal/tui/         Bubble Tea terminal UI: a root model plus one subpackage per
                      tab and a few shared subpackages
```

`pkg/client` — основной публичный пакет, и он намеренно **использует только
stdlib** — ни одного стороннего импорта, — так что от клиента можно зависеть,
не таща за собой OTel SDK, MCP SDK и другие тяжёлые зависимости
наблюдаемости/интеграций. Шов наблюдаемости — это интерфейс `Hook` только на
stdlib (см. [Руководство по библиотеке — Хуки наблюдаемости](library-guide.md#хуки-наблюдаемости));
конкретные реализации живут в `pkg/observe` (OpenTelemetry) и будущих пакетах,
у каждого свой набор зависимостей, так что пользователи платят только за то,
что импортируют. Всё, что находится под `internal/`, является реализацией,
которую компилятор запрещает импортировать внешнему коду, поэтому слои CLI/TUI
можно свободно рефакторить. И CLI, и TUI — тонкие вызывающие стороны
`pkg/client`. `go install github.com/SamyRai/go-z-ai@latest` собирает корневой
`main.go` в бинарник `go-z-ai`.

## Соглашения CLI

Обработчики команд, которым нужен клиент API, регистрируются как
`RunE: runWithClient(runX)` и принимают уже разрешённый `*client.Client` как
третий параметр — `runWithClient` (в `internal/cli/common.go`) разрешает его
один раз через `getClient`, так что обработчикам не нужно повторять
преамбулу с разрешением и проверкой в каждом из них. Сам приоритет учётных
данных живёт в `resolveConfig` (флаг → `--account` →
`ZAI_API_KEY` → активный аккаунт), он покрыт юнит-тестами в
`credentials_test.go`. Та же функция разрешает регион (`--region` →
`ZAI_REGION` → сохранённый регион аккаунта) и остальные глобальные настройки.

Формат вывода единообразен: каждая команда, печатающая результат,
регистрирует общий флаг `--format` через `addFormatFlag` и рендерит через
`emit(cmd, v, textFn)`, который выдаёт красивый JSON для `--format json`, а
иначе запускает читаемый человеком `textFn`. Прогресс-сообщения
(`progressf`) идут в stderr, поэтому stdout остаётся валидным JSON.

## Фасад запросов

Каждый метод сервиса проходит через единый путь запроса — сервисы никогда не
создают собственный `http.Request` или `http.Client`. Сервис описывает свой
вызов как `apiRequest` (метод, путь, тело и, при необходимости, базовый URL,
API-ключ, дополнительные заголовки, multipart-форма и атрибуция для хуков) и
передаёт его одной из этих точек входа `Client`, каждая из которых опирается на
`open`:

```text
doRequest(ctx, method, path, body, result)  // the common case: do() with the defaults
do(ctx, apiRequest, result)                 // open, then JSON-decode the body into result
doRaw(ctx, apiRequest)                      // open, then return the raw body (audio, file downloads)
streamSSE(ctx, c, apiRequest, decode)       // open, then decode the body incrementally (see Streaming)
        every one of them goes through Client.open(ctx, apiRequest) → *attempt
```

`open` отвечает за аутентификацию, повтор/backoff, разбор ошибок и жизненный
цикл хуков наблюдаемости для каждого эндпоинта. Поля маршрутизации, оставленные
пустыми в `apiRequest`, берутся из конфигурации клиента: нет базового URL —
`Config.BaseURL`, нет API-ключа — `Config.APIKey`. Сервис, которому нужен
другой хост (Agents, monitor, biz, Anthropic), задаёт `baseURL` через метод
`Region`; тот, которому нужны другие учётные данные (Embeddings, Moderations),
задаёт `apiKey` — он никогда не обходит `open`.

**Парность хуков.** `open` возвращает `attempt`: открытый 2xx-ответ плюс
состояние хука той попытки, которая его породила. Каждая попытка вызывает
`OnRequest`, а затем ровно один завершающий хук — `OnResponse` или `OnError`.
Неудачная попытка, которая будет повторена, вызывает `OnError` перед
backoff, а вызывающая сторона `open` завершает успешную попытку через
`succeed` или `fail`. Поэтому span, начатый в `OnRequest`, всегда можно
закончить.

**Multipart-загрузки** (файлы, транскрипция аудио, разбор документов) — это
`apiRequest` с заданным `form`. Они тоже проходят через `open`, но никогда не
повторяются: повторная загрузка файла при временном сбое — это решение
вызывающей стороны, а не безопасное поведение по умолчанию.

**Конверт monitor/biz.** API квоты (monitor) и аккаунта (biz) оборачивают
каждый ответ в `Envelope[T]` и сообщают о бизнес-сбоях внутри тела HTTP 200.
`fetchEnvelope` декодирует конверт и превращает сбой в `*APIError`
(классифицируется по коду конверта, когда тот повторяет HTTP-статус), так что
сервис, вернувший `Envelope`, уже завершился успешно, и вызывающая сторона
читает только `Data`.

## Потоковая передача

`stream.go` реализует server-sent events как итератор Go. `Chat().Stream` и
`Anthropic().Stream` возвращают `iter.Seq2[T, error]`; `streamSSE` выполняет
весь поток синхронно внутри итератора — без goroutine-производителя и без
канала, — так что выход из цикла `range` прекращает чтение и закрывает тело
ответа, а отмена контекста прерывает заблокированное чтение. `scanSSE` — общий
построчный парсер; каждый протокол поставляет небольшой декодер
(`decodeChatStream` в `chat.go`, `decodeAnthropicStream` в `anthropic.go`).

Ошибка, доставленная внутри потока, — фрагмент `{"error": ...}` в стиле
OpenAI или Anthropic `event: error`, — завершает поток с `*APIError`,
построенным тем же классификатором, что и HTTP-ошибки (`errors.go`). Хуки
видят каждый декодированный фрагмент через `OnStreamChunk`; попытка
завершается `OnResponse` при чистом окончании либо `OnError` при сбое в
середине потока или досрочном выходе (`context.Canceled`).

## Дизайн повторных попыток и тайм-аутов

- `Config.Timeout` ограничивает установку соединения + TLS-рукопожатие +
  ожидание заголовков ответа — намеренно **не** весь `http.Client.Timeout`,
  который обрезал бы долгое чтение `Stream` посреди генерации.
- Неудачная попытка повторяется, когда она повторяема: сбой транспорта
  (сервер так и не ответил) либо `*APIError`, помеченный как повторяемый, —
  HTTP 429 и 5xx, а также бизнес-коды, которые `errors.go` помечает как
  временные. Коды ошибок, которых нет в таблице, классифицируются только по
  HTTP-статусу, так что повторяются лишь троттлинг и сбои на стороне сервера;
  ошибки аутентификации, квоты и параметров — нет.
- Backoff экспоненциальный от `Config.RetryDelay` с джиттером (до 25%).
  Заголовок `Retry-After` (задержка в секундах или HTTP-дата) побеждает, если
  присутствует. Любая отдельная задержка ограничена 30 секундами. Цикл
  повторов ограничен `Config.MaxRetries` (по умолчанию 3; `-1` отключает
  повторы). Каждая повторная попытка сначала проверяет `ctx.Err()`, так что
  отменённый контекст прерывается немедленно, а не досыпает задержку.
- Потоковая передача повторяет только *попытку соединения* — как только
  SSE-поток действительно начался, сбой в середине потока доносится до
  вызывающей стороны, а не молча повторяется (нет способа узнать, какую часть
  ответа вызывающий уже получил).

## Почему некоторые сервисы обращаются к другому хосту

`Region` (`region.go`) — единственный владелец URL шлюзов: каждый базовый URL
в `pkg/client` — и каждый генератор конфигов в `internal/coding` — выводится из
`Region.Host` плюс одного пути корня API. Корни — это `Region.PaaSBaseURL`,
`CodingBaseURL`, `AnthropicBaseURL`, `ResponsesBaseURL`, `MonitorBaseURL`,
`BizBaseURL`, `AgentsBaseURL` и `MCPServerURL(name)`; `ConsoleURL` — веб-консоль,
а `BaseURLFor(AccountType)` выбирает корень чата для типа аккаунта.
Константы уровня пакета (`DefaultBaseURL`, `BigModelBaseURL`, ...) — те же
значения для двух шлюзов.

| Сервис | Базовый URL | Почему |
|---|---|---|
| Chat, Models, Images, Videos, Audio, Voice, Files, Batch, Tools, Rerank, ... | `Config.BaseURL` — по умолчанию `Region.PaaSBaseURL()` (`/api/paas/v4`). Ключ Coding Plan направляется на `Region.CodingBaseURL()` (`/api/coding/paas/v4`) через задание `Config.BaseURL` (CLI делает это по типу аккаунта) | Общий случай. Явный `Config.BaseURL` всегда побеждает. |
| Embeddings, Moderations | `BigModelBaseURL` (`open.bigmodel.cn`), аутентификация через `Config.ChinaAPIKey` | Документированы только на китайской платформе; `api.z.ai` отвечает 1211 Unknown Model для проверенных моделей. Живая верификация подтвердила, что обычный ключ z.ai аутентифицируется одинаково на обеих платформах, поэтому `ChinaAPIKey` по умолчанию откатывается к `APIKey`. |
| Anthropic Messages | `Region.AnthropicBaseURL()` | Отдельный Anthropic-совместимый корень. |
| Responses (протокол Codex) | `Region.ResponsesBaseURL()` — `/api/v1` | Отдельный корень протокола OpenAI Responses, документированный для GLM Coding Plan (docs.z.ai/devpack/tool/codex). |
| Квота/использование (monitor), аккаунт (biz), определение типа аккаунта | `Region.MonitorBaseURL()`, `Region.BizBaseURL()` | Привязаны к региону, так что китайский ключ достучится до эндпоинтов своего региона. |
| Agents | `Region.AgentsBaseURL()` — голый корень `/api`, без `/paas/v4` | Проверено на живую — вложение `/v1/agents` под базовый URL chat-completions возвращает 404. |

### Выбор регионального шлюза (Config.Region)

Z.AI обслуживает то же семейство моделей GLM с двух региональных шлюзов:
международного хоста `api.z.ai` и зеркала для материкового Китая
`open.bigmodel.cn`. `Config.Region` (`RegionGlobal` по умолчанию или
`RegionChina`) выбирает хост для каждого регионально-зависимого сервиса —
monitor, biz, agents, Anthropic Messages, Responses и определения типа
аккаунта, — и служит значением по умолчанию для `Config.BaseURL`, когда тот
пуст, так что `RegionChina` переносит на `open.bigmodel.cn` и чат. Явный
`Config.BaseURL` по-прежнему побеждает для корня chat/PaaS. Embeddings и
Moderations всегда используют `BigModelBaseURL`.

Из CLI `--region {global,china}` или `ZAI_REGION` (псевдонимы: `cn`,
`bigmodel`, `west`) выбирает каждый эндпоинт, а `--base-url` переопределяет
только корень chat/PaaS. Неизвестное значение откатывается к global, а не
вызывает ошибку, поэтому опечатка никогда не блокирует постороннюю команду.
Сохранённые аккаунты запоминают регион, в котором был выпущен их ключ;
`accounts add` определяет его, а `Account.ResolvedBaseURL` выводит корень чата
из типа аккаунта и региона, так что ключ нельзя направить на неверный
эндпоинт.

Хосты китайского зеркала для monitor/biz/agents смоделированы зеркалированием
структуры путей `api.z.ai` на `open.bigmodel.cn` и помечены
`NOT VERIFIED LIVE` в `region.go` — китайская платформа прошла живую
верификацию на предоставление той же OpenAPI-поверхности для `/models` и
`/chat/completions` (см. `BigModelBaseURL`), но хосты monitor/biz/agents на
стороне Китая пока не зафиксированы ни в одной cassette. Зафиксируйте их через
`ZAI_RECORD=1`, если у вас есть китайский ключ с соответствующими правами.

## Соглашение о живой верификации

Собственные SDK и документация Z.AI иногда расходятся между собой, а иногда
— с тем, что реально возвращает живой API (эндпоинт, заявленный как
необязательный, но возвращающий 400 без него; ошибка, встроенная в тело
ответа 200; поле с разным типом в двух официальных SDK). Вместо того чтобы
доверять одному источнику, новые сервисы здесь проверяются реальным вызовом
API, а взаимодействие записывается как cassette
[go-vcr](https://github.com/dnaeon/go-vcr)
(`pkg/client/testdata/cassettes/`) и проигрывается в `ModeReplayOnly`,
поэтому тестовый набор никогда не обращается к сети.

Два файла в `pkg/client` ведут работу по живой верификации, с разными
ролями: **`live_replay_test.go`** содержит тесты `Test*Live`, которые
проигрывают зафиксированные cassette как замороженные находки (проверки
прав, аномалия 200-со-встроенным-сбоем, утверждение об одном ключе для
нескольких хостов); это текущий журнал того, что подтверждено и почему это
важно. **`live_verify_test.go`** содержит инструмент записи `TestVerify*` —
каждый тест SKIP-ается, пока вы не захватите новую cassette успешного пути
через `ZAI_RECORD=1`, после чего её проигрывает; это список дел для форм,
ожидающих реального захвата (см. [Дорожную карту](roadmap.md)).

Если вы расширяете сервис, см.
[Участие в проекте § соглашение о живой верификации](../../CONTRIBUTING.md)
прежде чем добавлять новую cassette.

## Расширение таблицы структурированного поиска

Несколько типов в этой кодовой базе сопоставляют небольшое замкнутое
множество заданных API значений с человекочитаемыми метаданными через
таблицу плюс функцию поиска, а не через цепочку `if`/`switch`-условий.
Самый наглядный пример — `modelsCatalog` из `pkg/client/models_catalog.go`:
каждая строка — это `ModelCatalogEntry`, несущая размер контекста модели,
лимит вывода, цены, `Capabilities` (`CapText`, `CapVision`, `CapVideo`,
`CapFile`, `CapThinking`, ...) и `ReasoningEfforts`. Связанные строки
разделяют наборы возможностей и списки effort (`capsReasoning`,
`capsMultimodal`, `effortsGLM53`), так что они не могут разойтись.

```go
{
    ID: "glm-5.3-flash", Family: "GLM-5", Tier: "flash", Name: "GLM-5.3-Flash",
    Capabilities: capsMultimodal, ReasoningEfforts: effortsGLM53,
    ContextSize: ctx1M, MaxOutput: out128K, Pricing: usd(0.15, 0.03, 0.50),
    ...
},
```

Когда Z.AI добавляет модель, изменение носит аддитивный характер (добавить
строку) и локализовано; всё, чего нет в таблице, по-прежнему появляется из
`/models` с неполными данными, а не жёстко проваливается. Поиск идёт по
точному ID, затем по датированному снимку каталогизированного ID
(`findCatalogEntry`), а `ModelDetails.HasCapability` — единственное место, где
решается вопрос о возможности, так что фильтры CLI, TUI и библиотеки
согласованы. Та же форма встречается в `internal/coding` — реестр `Tools`
(`tools.go`, по одному `tool_*.go` на инструмент), реестр `MCPServers`
(`mcp.go`) и список `Plans` (`plans.go`). Предпочитайте эту форму ещё одной
условной ветке, когда вы добавляете новое распознаваемое значение к
существующему понятию.

`modelsCatalog` — также решение проблемы доступности данных: эндпоинт
`/models` Z.AI возвращает лишь «голую» OpenAI-форму `{id, object, created,
owned_by}`, поэтому без обогащения каждая ячейка `Context`/`Pricing`/
`Capabilities` отображается как `-`/`0`. `ModelsService.List` пропускает
каждую декодированную модель через `enrichModel`, который накладывает поля
каталога, но позволяет **живым значениям API побеждать**, когда присутствуют
оба, — так что в тот день, когда Z.AI начнёт присылать `max_context` или
`pricing` в `/models`, настоящие числа вступят в силу без изменения кода.
Цены и размеры контекста перенесены с
<https://docs.z.ai/guides/overview/pricing> и страниц моделей и требуют
периодического ручного обновления (API не сигнализирует об их изменении);
заголовок файла несёт дату «последней верификации». Константы `Default*Model`
в том же файле (`DefaultModel`, `DefaultFastModel`, `DefaultVisionModel`,
`DefaultOCRModel`, `DefaultASRModel`, `DefaultTTSModel`) — это значения по
умолчанию для CLI, TUI и генераторов конфигов инструментов для кода, так что
обновление каталога обновляет их все разом.

## Безопасность файлов учётных данных

И `internal/accounts` (хранилище нескольких аккаунтов), и `internal/coding`
(хранилище учётных данных GLM Coding Plan плюс все конфиги сторонних
инструментов, которые оно пишет — Claude Code, Codex, OpenCode, Crush, Factory
Droid) пишут через `internal/atomicfile`: временный файл в том же каталоге, а
затем переименование, а не прямая запись по месту. Сбой или kill в процессе
записи оставляет исходный файл нетронутым, а не обрезанным. Файл-симлинк
сначала разрешается, так что сама ссылка сохраняется.

Некоторые из них — реальные конфиги *других программ*, в которые выполняется
слияние, а не файлы, которыми этот проект владеет безраздельно, поэтому
`internal/coding` пишет их через `atomicfile.WriteWithBackup`: перед первой
перезаписью он копирует существующий файл в `<path>.zai.bak` и никогда не
заменяет эту резервную копию, а `configfile.go` правит только принадлежащие
ему ключи, сохраняя всё остальное. Он читает и пишет JSON или TOML по
расширению файла (`config.toml` у Codex); перезапись TOML отбрасывает
комментарии, как и у официального помощника, а резервная копия хранит
оригинал. Файлы, содержащие ключ, создаются с правами `0600`; каталоги —
`0700`.

## TUI

`internal/tui` — программа на [Bubble Tea](https://github.com/charmbracelet/bubbletea)
(v2) с одной вкладкой на подпакет (`chat`, `models`, `usage`, `accounts`,
`coding`, `media`, `tools`). Каждая вкладка — независимая `tea.Model` со
своими `Update`/`View`; корневая модель выполняет диспетчеризацию между ними.
Длительная работа (вызов API, файловая операция) оборачивается в замыкание
`tea.Cmd`, которое Bubble Tea запускает в собственной goroutine — код,
вызываемый из `tea.Cmd`, не должен рассчитывать, что изменяемое состояние
уровня пакета свободно от конкуренции (например, мутировать
`http.DefaultClient`); именно поэтому `internal/coding/validator.go` строит
новый `client.Client` на каждый вызов.

### Файлы и подпакеты

| `screens.go` | Необязательные интерфейсы, которые может реализовать экран и которые проверяет корень (`streamer`, `inputCapturer`, `helpProvider`, `refresher`, `chatModelSetter`/`chatModelGetter`) |

### Общая инфраструктура

Хром (заголовок, панель вкладок, панель, строка состояния, строка справки)
принадлежит корневой модели в `internal/tui/root.go`; каждый экран
рендерит только своё тело. Несколько сквозных элементов живут вне экранов,
чтобы их можно было разделять без циклического импорта:

#### Верхний заголовок

Заголовок (`internal/tui/header.go`) — это одна строка: бейдж приложения
`go-z-ai` слева, выровненный вправо кластер контекстных бейджей и распорка
между ними, прижимающая бейджи к правому краю. Бейджи дают каждой вкладке
состояние с одного взгляда:

- **account** — имя активного аккаунта (или `none` в стиле предупреждения,
  когда аккаунт не задан, чтобы отсутствие учётных данных нельзя было
  пропустить).
- **type** — `pay-as-you-go` / `coding-plan`, поскольку он определяет, какое
  семейство эндпоинтов и какие функции (например, monitor-эндпоинты вкладки
  Usage) доступны.
- **plan** — `Global` / `China` из хранилища coding, выводится потому, что он
  молча меняет эндпоинт, с которым общаются вкладка Coding и интеграции
  агентов для кода. Показывается, только когда plan настроен.
- **model** — выбранная в данный момент модель вкладки Chat. Полезна на любой
  вкладке, потому что пользователи часто проверяют Usage или Models, составляя
  чат.

На узких терминалах заголовок последовательно отбрасывает бейджи: сначала plan
и type (оставляя account + model), затем model (остаётся только account),
чтобы имя приложения и самое существенное оставались видимыми. Бейджи строятся
через `uistyle.RenderBadge(label, value, valueStyle)` — приглушённая метка в
паре со значением, окрашенным по роли.

Строка-распорка располагается над панелью вкладок и под ней, чтобы у хрома
было пространство для дыхания; `chromeRows` учитывает обе распорки при расчёте
размера внутренней панели.

- **`internal/tui/uistyle`** — словарь стилей lipgloss и двойная
  светлая/тёмная палитра. Корневая модель разрешает палитру относительно
  реального фона терминала (`tea.BackgroundColorMsg`) и пересобирает каждый
  общий стиль через `uistyle.SetDark`, так что всё приложение следует теме
  терминала. Стили — это `var` уровня пакета, переприсваиваемые при смене темы;
  экраны читают их заново во время рендеринга.
- **`internal/tui/uimsg`** — общие типы сообщений (`Err`, `Status`, `Routed`,
  `CloseOverlay`, `OpenModelPicker`, `AccountChanged`, `PlanChanged`), чтобы
  экраны могли общаться с корнем, не импортируя его. `Routed` оборачивает
  асинхронный результат вместе с вкладкой-источником (`uimsg.Route` строит его
  из `tea.Cmd`), так что результат, запущенный на одной вкладке, всё равно
  попадёт туда после переключения пользователя.
- **Оверлеи** — единственный слот `overlay tea.Model` на корне, компонуемый
  поверх активного экрана через `lipgloss.Place` (`placeOverlay` в
  `internal/tui/overlay.go`). Пока он открыт, он владеет нажатиями клавиш;
  сообщения об изменении размера, цвета фона и маршрутизированные сообщения
  по-прежнему доходят до экранов под ним, чтобы те оставались правильно
  скомпонованными, когда оверлей закроется. Оверлей справки (`?` / `f1`),
  командная палитра (`ctrl+p`) и выбор модели чата (`ctrl+o` на вкладке chat
  либо «Switch chat model» в палитре) — все это оверлеи, принадлежащие корню.

### Клавиши

Глобальные (обрабатываются корнем до того, как клавишу увидит любой экран):

| Клавиша        | Действие                                         |
|----------------|--------------------------------------------------|
| `tab` / `shift+tab` | следующая / предыдущая вкладка              |
| `?` / `f1`     | переключить оверлей справки (все привязки); `?` вводится в сфокусированное текстовое поле как символ |
| `ctrl+p`       | командная палитра (нечёткий поиск по действиям всего приложения) |
| `ctrl+c`       | выход (или отмена идущего потока чата)           |
| клик мыши по панели вкладок | переключить вкладку                 |
| колесо мыши    | прокрутить активную область просмотра / список   |

Привязки конкретных экранов показаны в строке справки внизу и в оверлее
справки.

### Адаптивная раскладка

Вкладки Models и Usage используют три уровня ширины:

- **≥ 100 колонок** — двухколоночные раскладки (Models: таблица + живой
  предпросмотр; Usage: квота и тепловая карта рядом).
- **70–99 колонок** — одна колонка, полные строки таблицы/тепловой карты.
- **< 70 колонок** — компактно: таблица Models отбрасывает колонку CAPS и
  сокращает заголовки цен; тепловая карта Usage сворачивается до сводок
  по одной строке на раздел; панель вкладок переключается на компактную форму
  из голых названий вкладок.

Ниже **60×22** корень рендерит только центрированное сообщение «Terminal too
small» с просьбой об окне не меньше 60×22 вместо перекрывающегося хрома.
Экраны по-прежнему получают `WindowSizeMsg` и ограничивают снизу свои
размеры, так что возврат за порог возобновляет корректно скомпонованное
приложение без дополнительной работы.
